# Частина A: Підхід до автоматичного покриття квізу Charlie

## Чому класичний підхід тут не працює

Класичний E2E-тест фіксує послідовність кроків: "натисни тут → заповни це → перейди далі". Для квізу Charlie це створює тести, які:
- Ламаються при кожній зміні кроків або їхнього порядку
- Працюють тільки для одного A/B-варіанта
- Вимагають переписування щоразу, коли додається новий екран

Тому потрібен підхід, який **відокремлює бізнес-результат від шляху до нього**.

---

## Три шари тестування

### 1. Детерміновані перевірки (що ТРЕБА перевіряти автоматично)

**Бізнес-результат** — єдине, що має бути стабільним попри будь-які A/B:
- Після проходження квізу створюється акаунт користувача
- Після проходження квізу бронюється пробний урок
- API-контракт: відповіді сервера мають правильну структуру та статуси

**Як перевіряти:**
- Перехоплення мережевих запитів (network interception): ловимо POST-запити на створення користувача та бронювання
- UI-верифікація: presence of success/confirmation screen
- API-верифікація (якщо є доступ до адмін-токена): запит до API підтверджує створення сутностей

**Чому саме так:** Бізнес-результат не залежить від UI-варіанта. Незалежно від того, який A/B-тест активний і скільки кроків у квізі — фінальний outcome той самий: user + booking.

### 2. AI-агентні перевірки (що віддати AI)

**Навігація по динамічному UI:**
- AI-агент з vision (Claude/GPT-4o) отримує screenshot кожного кроку
- Приймає рішення "що натиснути" на основі візуального контексту
- Може адаптуватися до нових кроків без змін коду

**Візуальна цілісність:**
- Чи рендерився кожен крок без помилок
- Чи є клікабельні елементи на кожному кроці
- Чи немає "мертвих" екранів де застрягає користувач

**Чому AI:** Класичний тест зламається при зміні тексту кнопки з "Далі" на "Продовжити". AI-агент побачить кнопку й натисне її незалежно від тексту.

### 3. Що НЕ варто тестувати автоматично

- **Конкретні тексти A/B-варіантів** — вони змінюються by design
- **Точну кількість кроків** — може бути 15, може 25
- **Порядок кроків** — може змінитися завтра
- **Конкретні стилі/кольори** — не є бізнес-вимогою
- **Тексти маркетингових блоків** — контролюються продуктовою командою

**Чому:** Тести на ці речі будуть генерувати false-positive шум, який знецінить всю автоматизацію.

## Як рішення переживає зміну A/B-варіанта

### Адаптивний навігатор (Variant 1)

Замість хардкоду кроків, навігатор працює за евристиками:
1. **Є clickable cards?** → Обрати першу
2. **Є input fields?** → Заповнити тестовими даними
3. **Є кнопка "Продовжити"/"Далі"?** → Натиснути
4. **Дійшли до success screen?** → Зупинитися, підтвердити результат

Це працює тому що **всі** варіанти квізу мають однакову механіку: вибір опцій → заповнення даних → підтвердження.

### AI-агент (Variant 2)

Ще стійкіший: на кожному кроці "бачить" сторінку й приймає рішення. Навіть радикальна зміна UI не зламає тест, якщо людський користувач зможе пройти квіз.

### Що може зламати тести?

- Зміна самого бізнес-результату (вже не створюється user) — це реальний баг, тест повинен впасти
- Квіз стає 100% broken (всі кнопки disabled) — це реальний баг
- Зміна домену/URL structure — потребує оновлення конфіга

## Інтеграція в CI/CD

### Рекомендований підхід: за розкладом + на ключові PR

| Тригер | Що запускати | Чому |
|--------|-------------|------|
| **Кожні 4 години (cron)** | Повний прохід квізу (Variant 1) | Ловить поламки від A/B змін, інфраструктурних проблем, сторонніх сервісів |
| **PR в quiz-related code** | Швидкий smoke (перші 5 кроків + assertion що не crash) | Запобігає деплою broken quiz |
| **Deploy на stage** | Повний прохід (обидва варіанти) | Підтверджує що деплой не зламав критичний шлях |

### Чому не на кожен PR?

1. Квіз має побічні ефекти (створює реальні записи) — надмірний запуск засмічує stage
2. Повний прохід займає 30-60 секунд (з AI-агентом — більше), що уповільнює CI
3. Більшість PR не торкаються quiz-коду

### Чому cron а не тільки PR?

A/B-тести змінюються незалежно від деплоїв (через feature flags/remote config). Cron ловить breakages, які PR-pipeline пропустить.

## Ризики та обмеження

### Технічні ризики

| Ризик | Мітігація |
|-------|-----------|
| AI-агент може "застрягти" на незнайомому кроці | Max iterations + fallback до евристичного навігатора |
| API Claude може бути недоступний | Graceful skip AI-тестів, бізнес-тест (Variant 1) працює без AI |
| Stage environment down | Retry logic + alerting окремо від тестів |
| Quiz створює реальні записи | Використовувати маркер у email (test.quiz.*@example.com) для auto-cleanup |

### Обмеження підходу

1. **Не перевіряє UX якість** — тест підтверджує що квіз можна пройти, але не що він зрозумілий людині
2. **Евристичний навігатор може обрати "неправильний" шлях** — але для бізнес-результату це не важливо
3. **AI-агент коштує грошей** — кожен прохід ~$0.02-0.05 (screenshots + Claude Sonnet)
4. **Не покриває всі A/B-варіанти одночасно** — один run = один варіант. Щоб покрити всі, потрібно або контролювати feature flags, або запускати N разів
5. **Network interception може пропустити зміну API endpoints** — потребує оновлення patterns якщо API змінюється

### Що б зробив далі за більше часу

- API-level verification через адмін-панель (Bearer token)
- Автоматичний cleanup тестових записів після кожного проходу
- Visual regression на ключових кроках (не всіх — тільки фінальний екран)
- Паралельний запуск з різними feature flags для покриття A/B
- Alerting в Slack при падінні cron-тестів
- Метрики: час проходження квізу, кількість кроків (для відстеження регресій в UX)
